# NEXUS Gate10 - 簡易CRM

営業部の商談進捗を月中に把握し、更新が止まった案件を見つけるためのMVPです。

## 起動手順

Node.js 22.5以上が必要です。外部パッケージは使用していません。

ターミナルで、このリポジトリのフォルダへ移動してからサーバーを起動します。

```bash
cd NEXUS-Gate10
npm start
```

`npm`を使わずに起動する場合は、次のコマンドでも同じように起動できます。

```bash
node src/server.js
```

ターミナルに `Gate10 CRM: http://localhost:3000` と表示されたら、ブラウザで [http://localhost:3000](http://localhost:3000) を開いてください。サーバーを起動したターミナルは、利用中は閉じないでください。

> [!IMPORTANT]
> `public/index.html`をダブルクリックするなど、`file://`から直接開いても動作しません。必ず上記の手順でサーバーを起動し、`http://localhost:3000`へアクセスしてください。

初回起動時にSQLiteデータベースと24件のダミー商談が作成されます。

テストは次のコマンドで実行できます。

```bash
npm test
```

## 本当に解決すべき課題

営業担当の記録が不統一・未入力のため、管理者が月中に案件の進捗と停滞を把握できないことです。

## 3. 成功指標

MVPでは、次の状態を満たせば課題解決の可能性を検証できたと判断します。

- 営業部長が月中の任意の時点で、20件以上の商談について担当者・フェーズ・受注予定日・最終更新日・次回アクションを一覧で確認できる。
- 最終更新から14日以上経過した進行中の商談を一覧上で識別でき、少なくとも3件の停滞案件を1分以内に見つけられる。
- 営業担当が必要最小限の項目で商談を登録し、商談詳細からフェーズと次回アクションを更新できる。
- 登録・更新した内容が一覧へ反映され、月末の集計を待たずに最新状況を確認できる。

## 4. 作ったもの（Must / Should）

| 機能 | 区分 | 実装状況 |
|---|---|---|
| ユーザー・フェーズ・商談の3テーブル | Must | 実装済み。SQLiteでリレーションを保持 |
| 24件のダミー商談 | Must | 実装済み。停滞・進行中・受注・失注を含む |
| 商談一覧 | Must | 実装済み。担当者、フェーズ、受注予定日、最終更新日、次回アクションを表示 |
| 商談登録 | Must | 実装済み。進捗管理に必要な項目だけを入力 |
| 商談詳細 | Must | 実装済み。登録内容と現在の進捗を確認可能 |
| フェーズと次回アクションの更新 | Must | 実装済み。保存時に最終更新日時も更新 |
| 14日以上停滞した進行中商談の強調 | Must | 実装済み。受注・失注は停滞判定から除外 |

今回はMust機能の完成を優先したため、Should機能は実装していません。

## 5. 作らなかったもの（Won't）とその理由

| 機能 | 作らなかった理由 |
|---|---|
| ログイン・パスワード再設定 | 固定ユーザーと初期データで中核価値を検証でき、認証の作り込みは商談進捗の可視化に直接寄与しないため |
| 顧客マスタ管理 | MVPでは商談に顧客名を直接保持すれば一覧・登録・更新の検証ができるため |
| ダッシュボード・グラフ | データの蓄積前に集計画面を作るより、まず一覧で進捗と停滞を確認できることを優先したため |
| CSV入出力 | 既存Excelの項目や形式が統一されておらず、取込仕様の確定に時間がかかるため |
| 通知設定 | 停滞案件を一覧で強調することで、MVP段階では代替できるため |
| 活動履歴・監査ログ | 最新のフェーズと次回アクションを把握することを優先し、変更履歴の管理は次段階としたため |
| 担当者・フェーズの絞り込み | 24件程度であれば一覧でも検証できるため。件数増加後に優先して追加する |
| 今月の受注見込み集計 | 受注見込みの判定ルールや確度が未確定で、誤った数字を表示するおそれがあるため |

## 6. 仮定した内容

- 利用者は初期登録された営業部長1名、マネージャー1名、営業担当3名とし、ユーザー登録画面は不要としました。
- 商談フェーズは「初回接触」「ヒアリング」「提案中」「見積中」「受注」「失注」の6段階で固定しました。
- 「停滞」は、受注・失注を除く商談で最終更新から14日以上経過した状態と仮定しました。
- 商談の最新フェーズは商談テーブルのフェーズIDで保持し、更新時に上書きします。フェーズの変更履歴は保持しません。
- 顧客名は顧客マスタを作らず、商談ごとのテキストとして保持します。
- 商談登録時の次回アクションは任意、進捗更新時は次の行動を明確にするため必須としました。
- 受注予定日は日付のみを管理し、金額・受注確度・失注理由は今回の判断に不要としました。
- MVPは1台のPC上で動かす社内検証用とし、外部公開、複数拠点運用、バックアップは対象外としました。
- 手書きER図に合わせて3テーブルに絞り、Must機能の次回アクションを保存するため、商談テーブルに `next_action` を追加しました。

## 8. 積み残しと次にやること

1. 一覧・登録・詳細のモック画像を撮影し、READMEに記載した名前で保存する。
2. 担当者・フェーズによる絞り込みと、今月の受注見込み集計を追加する。
3. 実運用で必要なユーザー数、停滞日数、フェーズ遷移、受注見込みの判定ルールを営業部へ再確認する。
4. フェーズ変更履歴・活動履歴を追加し、誰がいつ更新したか追跡できるようにする。
5. 認証・権限管理、バックアップ、外部公開時のセキュリティ対策を追加する。
6. 異常系、同時更新、ブラウザ操作を含むテストを拡充する。

## 9. 振り返り

### 9-1. ヒアリングで聞いておけばよかったと思うことは何ですか。

「停滞」と判断する日数、現在使っているフェーズ名と遷移ルール、営業担当が更新できるタイミング、月中に部長が判断したい具体的な内容を、数値や実例まで確認すべきでした。また、成功指標を実運用後に測るため、現在の入力率・更新頻度・確認作業時間も聞いておけば、改善効果を比較できました。

### 9-2. 「作らない」と判断した機能のうち、今振り返って判断が正しかったと思うもの／間違っていたと思うものを挙げてください。

ログイン、顧客マスタ、ダッシュボード、通知を作らなかった判断は正しかったと考えます。これらがなくても、商談の登録・更新と停滞案件の把握という中核価値を確認できたためです。一方、担当者・フェーズの絞り込みは、案件数が増えた場合や部長が特定チームを確認する場合に一覧の使いやすさを大きく左右するため、Shouldとして時間を確保できれば実装すべきでした。

### 9-3. Gate1・Gate5で身につけた観点のうち、今回どれを使いましたか。また、意図的に使わなかった観点はどれで、それはなぜですか。

Gate1で身につけた、曖昧な依頼をそのまま実装せず、利用者・利用場面・困りごと・確認すべき点に分解する観点を使いました。Gate5で身につけた、入力値をサーバー側でも確認すること、外部キーで不整合を防ぐこと、失敗時に成功として扱わないことも取り入れました。一方、Gate5で扱った同時実行、詳細な例外系、厳密な権限管理は、3時間で中核価値を動く形にすることを優先して意図的に対象外としました。実運用へ進む場合は、これらを追加で設計・実装します。
